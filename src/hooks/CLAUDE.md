- **usePersistence.js** — **v17.16.10 (CT-2A-09): the write no longer happens inside a `setState` updater.** `saveBookings`/`saveBlocks` compute from the new `bookingsRef`/`blocksRef` mirrors, then `setState` and write as plain statements — `useWaitlist.js`'s shape, and the one CLAUDE.md's own gotcha row has prescribed since v16.0.0 while this file did the opposite. Verified live against DEV rather than by reading: a form save moved the server `status` and `updatedAt`, and two back-to-back quick actions produced a second write whose `baseUpdatedAt` was EXACTLY the first write's `updatedAt` — which is the property that proves the mirror is current, since a stale one would have carried a superseded base and been CAS-rejected. `saveBlocks` advanced `tableBlocksRev` by exactly +1. **v17.16.9 (CT-2A-07): an exhausted write is PARKED, not dropped** — kept in `parkedRef` with a label, mirrored to the banner as `parkedWrites`, and cleared by `retryParked` (a fresh round of automatic attempts on resynced data) or `discardParked` (accept the loss). **The finding's own account of why the old drop was bad does not survive running it**, and the correction is the load-bearing part: it says the optimistic `setBookings` is never reverted, so screen and server disagree "until the next echo" — but `drainPending` is called from exactly two places, `resync().then` and the live `bookings` onValue, and BOTH set local state to server truth and `clearStale()` immediately before it, in the same commit. - **usePresence.js** — v17.3.0 — real-time device presence for the connection-dot popover. Subscribes to .info/connected → on connect pushes ONE ephemeral child `presence/{pushKey}` {email, ua (deviceLabel from userAgent), since:serverTimestamp} with onDisconnect().remove() (self-cleans on tab-close/sleep/drop); subscribes to `presence` → returns {devices[], myKey, offset}. **v17.8.0: onDisconnect alone leaks.** It arms ONE fire-once server op; if the socket drops between arming it and the `set()` landing, the server fires the (empty) removal and the SDK then REPLAYS the queued `set()` on reconnect — writing a child with no onDisconnect, i.e. immortal. Reordering the calls only moves the window. So a live connection re-proves itself with a 45s `lastSeen` heartbeat, a child counts as connected only inside STALE_MS (150s), and children past PRUNE_MS (10min) are deleted. **The staleness filter is enforced on READ**, so a pre-existing leak is hidden the moment the code runs, with no write needing to succeed; deletion is 4× more conservative because hiding is reversible and deleting isn't. The prune is ARMED on connect and CONSUMED by the next `presence` snapshot — it cannot run in the `.info/connected` handler, which resolves before the first snapshot exists (the first version did, and never fired). A pre-v17.8.0 child has no `lastSeen`, so the filter falls back to `since`. `.info/serverTimeOffset` is subscribed because the whole model compares a serverTimestamp to local time. EXEMPT from the CAS/revGuard rule (ephemeral, per-connection; the prune touches other keys but only to delete already-dead ones, which is idempotent); **v17.16.7: `presence` now needs a rule of its own** — `presence/$key: {".write": "auth != null"}`. It has no `.validate` and the permission is identical to what it always inherited, so nothing about the node changed; what changed is that the ROOT `.write` grant it inherited FROM is gone (CT-2A-04/06), and a path with no grant is unwritable. It was the one node the pre-fix probe broke, which is why it is called out here rather than left to the general rule

- **useRevealRows.js** — extracted per-row ease-in/out lifecycle (renderIds/openIds/sig/prune) shared by LateBanner + WaitAvailBanner (v16.3.0). **v17.15.0 adds an optional `resetKey`: a REPLACEMENT is not a change, and this lifecycle cannot tell them apart on its own.** It holds a departed id mounted so its Reveal can collapse and mounts a newcomer closed so it can ease open — right for a notification arriving or resolving while you watch, wrong for a list swapped wholesale, which is what a date change does to the notification strip. Measured going 22→23 Aug: **~550ms of the previous day's notifications** under the new day's heading (the wrong information, not merely slow), and a transient two-section state belonging to neither day that took the pane 70px of height to finish 2px from where it started. On a change of `resetKey` it re-seeds exactly as on FIRST MOUNT — which is what its own initializers already describe — so ids common to both lists keep their place and do not blink. The re-seed runs DURING RENDER, not from an effect, and that is load-bearing: it makes the first COMMITTED dom the new list, so the caller's layout effect can measure the height it is leaving against the height it is arriving at. The ref writes it implies (`prevKeys`, the prune timers) are in a layout effect — layout effects all run before any passive effect, so `prevKeys` is current before the membership diff reads it, and a ref written during a render that may be discarded is not

- **useModalStack.js** — v17.14.0 — ONE ordered stack of open modal surfaces, replacing eighteen independent visibility booleans in App. `MODAL_Z` is the app's z-order ASCENDING — exactly the old hand-written Escape chain read bottom-up, now data — and `topModal(stack)` is what Escape acts on; push order only breaks a tie. `applyModal` is the single writer: falsy closes, an updater function is applied to the current payload (ReminderEditor's `setDraft` needs that), re-opening an already-open modal replaces its payload IN PLACE rather than moving it to the top, and an unchanged payload returns the same reference. **The defect it removes is structural**: the set of open surfaces and their order were spread across FIVE hand-written lists kept in step by nothing, and `showWaitlist` was missing from four of them — its Overlay could not be closed with Esc, did not suppress single-letter shortcuts and did not mark the page behind it `inert`. Two coverage guards in tests/modal-stack.test.js, both proven against known-bad input: every `modalOpen.<id>` / `setModalFns.<id>` App reads has a rank in `MODAL_Z` — both are now GENERATED from it, so a `setModalFor("…")`-style scrape of App stopped being a meaningful check the moment that happened; the guard that still bites is the read side, `modalOpen.<id>` with no rank yields no setter and no Escape action — and every rank has an `escapeAction` case

- **useDismissals.js** — v17.14.0 — the notification strip's four ✕-dismissal Sets, one mechanism (`late` · `overlap` · `wait` · `clash`). Their bodies were identical; what differed was the key (`clash` is keyed by PAIR via `clashRowId`) and the LIFECYCLE, and only the second is a real distinction. `late`/`overlap`/`wait` are today-only and monotonic within a day, so they are emptied on a date change (`DAY_DISMISS_KEYS`); `clash` PRUNES against its live pairs instead — a double-booking is the one notification whose point is that you go and fix it, so it clears and can recur — which covers the date change for free. **`clash` being absent from the day reset is correct, not drift.** Both identity properties are deliberate and were free before: a no-op returns the same object (so the prune effect cannot re-enter), and an untouched key keeps ITS Set by reference (so dismissing an overlap row does not invalidate the late banner's memo)

- **useArmAfterRelease.js** — v17.16.12 — a surface opened by a PRESS-AND-HOLD is inert until the pointer that opened it is released. `QuickStatusPopup` and `SplitMenu` both mount 400–450ms into a hold, as viewport-CENTRED cards portalled to `<body>`, so the finger that opened them is sitting on the card it just conjured and the release activates whatever is under it — the scrim (which closes the popup the instant it appears) or one of its own buttons (which changes a booking). **The signal is the RELEASE, not a delay**: a 300ms hold and a 3s hold behave identically, which is the whole reason this is a hook and not a `setTimeout` at each call site. Listeners are CAPTURE-phase because the card calls `stopPropagation`; `pointerdown` is in the list because a new press means the opening one is long over; the 2s timeout is a pure backstop against a surface that could otherwise stay inert forever, and is far longer than any hold-then-release on purpose. **Mount-scoped, which is only correct because all three call sites mount the popup conditionally** — an always-mounted popup would arm on the parent's mount and be armed before it ever opened. A new hold-opened surface takes this hook rather than a copy of it; v17.10.1 fixed the SELECTION half of this same defect on Android and left the activation half, which is how one shape became two versions apart.
