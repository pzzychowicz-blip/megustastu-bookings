Second: `optimise`'s day sort takes **`id` as a FIFTH key**, making it a total order. The four above it (locked, size desc, stated preference, start time) leave real ties and `Array.sort` is stable, so a tie fell through to ARRAY POSITION — and array order is not the same on two devices. Measured over 200 shuffled days: a varied day differs in 13/200, but the shape a service actually has (parties of 2 and 4, on the hour and half hour, nearly all auto — exactly where those four tie) differs in **138/200**, while the number of UNPLACED bookings differs in **0/200 in both**. So which table you get was a coin flip on two days in three; whether you get one never was, which is what makes the tie-break free. You cannot regress from "undefined", and the replacement is meaningful rather than merely stable: `genId()` is a base36 timestamp, so id order is CREATION order. **The later passes need no key of their own** — the swap pass's `others.sort` is equally partial but sorts a list derived from `day`, and stability propagates the fix (0/200 confirms it). **v17.16.2 gives it the shared time axis**: `pastCloseMins` MOVED here out of `usePersistence` (it needs the `hoursFor` live binding, which `day.js` must not take) — it was the one function in the repo that ever put now and a booking on a common ruler, and it was private to the one file no test could reach. `seatedElapsed(b,today,nowM)` is how long a seated party has been at the table, on the booking's own axis, **capped at that day's close** — the cap is what makes dropping the old `b.date === today` filter safe (uncapped, a booking left seated three weeks ago has a true elapsed time of 30240 minutes, which `syncLiveDurations` would write as its duration) and it is a CAP rather than a skip because skipping made the figure jump back to the stored duration the moment close passed, and made an existing test pass before 22:00 and fail after. Capping matches auto-complete's own `closeMins - toMins(b.time)`, so the live number and the frozen one meet instead of stepping. `seatedIsLive(b,today,nowM)` is the companion the `/code-review` added: the cap bounds the VALUE but never authorised a WRITE to another day's record, and without it `syncLiveDurations` rewrote the duration of a booking left seated three weeks ago on the next unrelated save (540 against a stored 90), enlarging the atomic patch where one malformed historical booking can reject a valid save. `liveBarDur` shares the test so the bar drawn and the duration stored can never disagree. `liveBarDur`/`occupancyEnd`/`applySeatedShift`/`lateMins` all take `today` now; `lateState` KEEPS its date filter while `freeingSoon` loses its, which is principled rather than inconsistent — `freeingSoon` is self-bounding (`0 < inMin <= win`) while lateness is unbounded backwards and a booking from a fortnight ago would read "20160 min late" for ever. `applySeatedShift` also REFUSES a shift outside `[0,1440)` of its own date: a start is stored as `HH:MM` against that date and `toTime` wraps modulo 24, so fixing only the axis would have traded a 24-hour duration for a 24-hour displacement onto yesterday. **BOTH bounds are load-bearing** — the first version checked only the upper one, and seating a booking dated TOMORROW projects `now` NEGATIVE, cleared every remaining guard and wrote `toTime(-60)` = `"-1:00"` as the time.
