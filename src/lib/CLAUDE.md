- **booking-logic.js** — pure functions (optimizer, sanitisation, derivations, daySummary). **v17.16.5 makes two of them answer for their consumers.** `isReadableTime(v)` + `sanitize`: the whitelist guarded TRUTHINESS (`b.time||"13:00"`) where every consumer needs a time `toMins` can take apart — so a stored `time: 2000` survived, reached the first reader and threw `t.split is not a function` at one of its 83 call sites, contained by v17.16.0's boundary but leaving the day unusable. Reachable from the SERVER, because v17.16.1's per-field rules check type and deliberately not format; this is that finding's client half. **The predicate is the consumer's requirement, not a format of its own** — kept iff `toMins` yields a finite number — because the one rule this function cannot break is that nothing currently working may move, and a `/^\d{2}:\d{2}$/` pattern would also move `"9:30"`, `"13:00:00"` and `"13:0"`. Its stated cost: `":"` (00:00) and `"25:99"` (1599) are KEPT, since neither crashes and normalising a record that renders is a different decision. `scheduledTime` falls back to the SANITISED time, never the literal — a booking moved to 19:00 must not claim it was scheduled for one. **v17.16.6 closes the sibling this left open**, at the CONSUMER and through **`isReadableBlock`, which is EXPORTED because there are TWO of them**. The first version guarded `getBlockSlots` alone, and `TimelineView`'s `BlockBar` filters `dayBlocks` by date and then calls `toMins(bl.from)` itself — so the placement path went safe while the same block still threw during RENDER, where the error boundary unmounts the whole tree. Proven on DEV against a real malformed block written straight to `tableBlocks`: with the filter the day renders normally, without it the app is replaced by "MGT Bookings hit an error". **The crash moved somewhere worse rather than closing** — the two-consumers-one-rule shape this file already records for the settings-tab list and the modal-visibility lists. `tests/booking-logic.test.js` now scans every file that hands a block's own `from`/`to` to `toMins` and fails if it does not know about the predicate. **Only the consumers that COMPUTE with the pair filter on it**: `DaySheet` and `BlockModal` merely print the two strings, cannot crash, and `BlockModal` is where somebody goes to REMOVE the block — hiding it there would take away the only repair. `sanitizeBlock` is a MINT and not a whitelist — its header says so, and says not to "finish" it by copying `sanitize`'s shape — so a default there would hand the block a window nobody entered and then PERSIST it on the next `saveBlocks`. The cost is stated at the site rather than hidden: the table is silently UNDER-blocked for minutes somebody meant to protect, which beats the day being unusable and leaves the stored record intact for whoever repairs it. `allDay` is exempt because it never reads the pair. **The two fallbacks are pinned together**, as `PlanView`'s `markStatus`/`fillFor` pair is: two tests prove the skip (against the restored pre-fix filter) and two more prove it does NOT widen — an `allDay` block with a malformed pair still spans the day, and `"9:30"` / `"13:00:00"` / `":"` still read, because the guard is `toMins` yielding a finite number and deliberately not a format. Second: `optimise`'s day sort takes **`id` as a FIFTH key**, making it a total order. The four above it (locked, size desc, stated preference, start time) leave real ties and `Array.sort` is stable, so a tie fell through to ARRAY POSITION — and array order is not the same on two devices. Measured over 200 shuffled days: a varied day differs in 13/200, but the shape a service actually has (parties of 2 and 4, on the hour and half hour, nearly all auto — exactly where those four tie) differs in **138/200**, while the number of UNPLACED bookings differs in **0/200 in both**. So which table you get was a coin flip on two days in three; whether you get one never was, which is what makes the tie-break free. You cannot regress from "undefined", and the replacement is meaningful rather than merely stable: `genId()` is a base36 timestamp, so id order is CREATION order. **The later passes need no key of their own** — the swap pass's `others.sort` is equally partial but sorts a list derived from `day`, and stability propagates the fix (0/200 confirms it). **v17.16.2 gives it the shared time axis**: `pastCloseMins` MOVED here out of `usePersistence` (it needs the `hoursFor` live binding, which `day.js` must not take) — it was the one function in the repo that ever put now and a booking on a common ruler, and it was private to the one file no test could reach. `seatedElapsed(b,today,nowM)` is how long a seated party has been at the table, on the booking's own axis, **capped at that day's close** — the cap is what makes dropping the old `b.date === today` filter safe (uncapped, a booking left seated three weeks ago has a true elapsed time of 30240 minutes, which `syncLiveDurations` would write as its duration) and it is a CAP rather than a skip because skipping made the figure jump back to the stored duration the moment close passed, and made an existing test pass before 22:00 and fail after. Capping matches auto-complete's own `closeMins - toMins(b.time)`, so the live number and the frozen one meet instead of stepping. `seatedIsLive(b,today,nowM)` is the companion the `/code-review` added: the cap bounds the VALUE but never authorised a WRITE to another day's record, and without it `syncLiveDurations` rewrote the duration of a booking left seated three weeks ago on the next unrelated save (540 against a stored 90), enlarging the atomic patch where one malformed historical booking can reject a valid save. `liveBarDur` shares the test so the bar drawn and the duration stored can never disagree. `liveBarDur`/`occupancyEnd`/`applySeatedShift`/`lateMins` all take `today` now; `lateState` KEEPS its date filter while `freeingSoon` loses its, which is principled rather than inconsistent — `freeingSoon` is self-bounding (`0 < inMin <= win`) while lateness is unbounded backwards and a booking from a fortnight ago would read "20160 min late" for ever. `applySeatedShift` also REFUSES a shift outside `[0,1440)` of its own date: a start is stored as `HH:MM` against that date and `toTime` wraps modulo 24, so fixing only the axis would have traded a 24-hour duration for a 24-hour displacement onto yesterday. **BOTH bounds are load-bearing** — the first version checked only the upper one, and seating a booking dated TOMORROW projects `now` NEGATIVE, cleared every remaining guard and wrote `toTime(-60)` = `"-1:00"` as the time. The pre-v17.16.2 code was safe there **by accident** (its `nowM >= scheduledEnd` test fired on the unprojected value), so the axis fix REMOVED a protection nothing pointed at; v17.12.0 `describeBooking(b,{tables})` — the ONE source for what a booking sounds like, read by the List card, the timeline block and the floor-plan table. It was three hand-written copies, two of them byte-identical; PlanView is why it takes an OPTION rather than becoming a second function (its subject is a table, so it prefixes "Table 3, " and must not repeat it), which is the mirror of `time-grid.js`'s `hourLabel`/`cutoffLabel`, where merging two apparent copies would have shipped a bug. State clauses (double-booked, overstaying, running late) stay at the call site — they describe how a block is DRAWN, not what a booking is. v17.14.0 fixed its table clause: `" and "` joined three tables as "5A and 5B and 6", so it is a list now ("tables 5A, 5B and 6") and the NOUN follows the count — a mega-combo of three or four tables is an ordinary Settings → Layout configuration. v17.14.0 also adds **`mergeSpans(spans)`** (merge overlapping [from,to) minute ranges, TOUCHING ones included — two clashes meeting at 20:30 are one contested stretch and a zero-width seam is an artefact) and gives **`bookingsAfterAction` a no-op identity contract**: it returns its INPUT array when the pass moved nothing, comparing on `undoKey`'s field set so the gate can never be narrower than the transform. It reuses **`undoKey`'s field set on purpose**: the first version compared `id:tables` alone and silently discarded the `duration` extension `syncLiveDurations` writes and the `_conflict` flag `applyOpt` writes, i.e. it was narrower than the thing it gated. `undoKey`'s separators became ASCII control characters in the same commit — `|` and `+` are reachable FROM THE DATA (a table id need only avoid `|`, so "1+2" collapsed `["1+2"]` and `["1","2"]`; `notes` is free text), and a collision reads as "nothing changed", which for undo means a snapshot is never taken. **v17.16.6 (CT-2A-11) finished that job**, because the comment left behind — "No text field in the app can produce a control character" — was an assertion nothing enforced and nothing was true of: `notes` is a `<textarea>`, `sanitize` writes it verbatim, `idOk` forbids only `|` in a table id, and no rule validates field FORMAT. `undoKey` now caret-ESCAPES `\u001b`–`\u001f` in every value, so the guarantee is a property of the function rather than a claim about the rest of the app. **Escape, never strip** — and the option first written down said strip: removing the bytes closes the boundary-shift collision by opening an identical one a character away (`"a\u001fb"` and `"ab"` become one key), which is the same failure with a different pair of values. The reachable collision is the ARRAY join, where ONE poisoned value suffices; the field join has fixed arity, so a shift changes the separator count and needs a SECOND poisoned field. Both sabotages are pinned in `tests/booking-logic.test.js` — the un-escaped key fails two tests, the stripping variant fails a different one v17.11.0: **`findClashes(list,date)`** → the PAIRS behind `findConflicts` — who clashes with WHOM, on which tables, over which minutes. The id set was enough for the only consumer there had ever been (the reconciler picks one booking out of it and does not care what it collided with); a block that must say "double-booked with Rita Camps on table 3" and a strip row that is ABOUT a pair can recover neither from `["p","r"]`. `findConflicts` is now derived from it and its existing tests are what prove the contract held; `verifyClean` deliberately keeps its own copy, because it short-circuits at the first clash and runs over every active date on every settled snapshot. Unbuffered, like the two functions whose loop it replaces — turning the turnaround setting on must never make an already-booked day start reporting clashes. **`tables` is the INTERSECTION and can be EMPTY**: `canAssign` also rejects a pair when each booking takes two or more tables from the same join cluster, and those sets need not intersect. Unreachable in the DEFAULT layout by pigeonhole (its biggest cluster is three tables, and two 2-subsets of a 3-set always share a member) but reachable with a join group of FOUR, which is a legitimate Settings → Layout edit — pinned in the tests, and callers must handle it rather than assume there is a table id to name. Also **`clashRowId(pair)`**, the stable identity of ONE clash, for the strip's per-row dismissal Set (keyed by PAIR, not by booking, so dismissing "Pau vs Rita" does not silence "Rita vs a third party"). Its separator is an ASCII control character for `undoKey`'s reason — a separator reachable FROM THE DATA is a collision waiting to happen, and `"_"`/`"-"` are already spoken for by recurring occurrence ids — written as the `\u001f` ESCAPE and never the raw byte, which is invisible in every editor, grep and diff. - **waitlist-match.js** — v17.8.0 — `placeWaitlist(...)`, the pass that decides WHICH TABLE the app offers each waiting party. - **reconcile.js** — v17.14.0 — the post-sync conflict reconciliation DECISION, extracted from the useEffect that had held it since v15.6.1. `dirtyDates(bookings,today)` finds the dates failing `verifyClean`; `reconcile(prev,dirty,blocks,autoOptimizer)` resolves them and returns `{next,changed}`. - **day.js** — **v17.16.11 adds `isReadableDate` / `stepDate`, over a private `stepUTC`** — the safe half of the date step, for the four sites that move the VIEWED date. `viewDate` is not always app-controlled: `SearchPanel`'s `onPick` calls `goToDate(b.date)` with a booking's STORED date and `searchBookings` never filters on date validity, so one booking holding `date: ""` — a shape `sanitize` itself emits — put an unparseable string into `viewDate` and `addDays` threw. **Two paths, two different failures, and the split is why the fix has two halves**: the arrows throw in an EVENT HANDLER, which no error boundary catches, so Next/Prev/`←`/`→` silently stopped working and left you stuck on that date; `WeekView` throws during RENDER and DID hit the boundary ("MGT Bookings hit an error"), which is why it takes a guard on the `anchor` its `ref`/`focus` seed from rather than a swapped stepper — `goMonth` throws on its own `toISOString()` and never goes through `addDays` at all. `isReadableDate` is DEFINED AS a zero-day step succeeding (the `isReadableTime`/`isReadableBlock` consumer's-requirement shape, taken one further so the predicate and the operation cannot drift), and is deliberately NOT a `^\d{4}-\d{2}-\d{2}$` pattern — `"2026-8-3"` navigates today and must keep navigating. `stepUTC` tests its OUTPUT rather than its input, because two of its three reject grounds are invisible from the input: `"275760-09-13"` parses and `+1` day is NaN, and `addDays("9999-12-31", 1)` used to return the ten-character garbage `"+010000-01"` from the expanded `±YYYYYY` form. **`addDays` stays STRICT and is now implemented over `stepUTC`** — a caller wanting the strict answer wants it, a caller wanting the safe one wants `stepDate`, and `tests/day.test.js` pins that it still throws on every input `stepDate` absorbs, so the two cannot be collapsed. Anchoring on today rather than refusing the jump is deliberate: the bad booking stays reachable, because it is the thing somebody has to go and repair (the `BlockModal` rule). v17.16.2 — the app's answer to two questions it had never answered once: **what day is it** (`todayStr()`) and **how do now and a booking share an axis** (`nowOn(dateStr,today,nowMins)`), plus `dayDiff` and `addDays`. **It imports NOTHING, and that is load-bearing**: `constants.js` needs `todayStr()` for `EMPTY_FORM` and `booking-logic.js` imports `constants.js`, so anything imported here could close that loop — a helper needing a live binding belongs in `booking-logic.js` instead (which is why `pastCloseMins` went there and not here). `todayStr` replaced 44 copies of `new Date().toISOString().slice(0,10)`, which answers in **UTC** while the app's clock is local (`getHours`) — and Me Gustas Tú is in the Canaries, WEST (UTC+1) from March to October, so for the first hour of every local day all summer the app believed today was yesterday: the Today button landed wrong, `optimizerActiveFor`'s branch inverted, and a walk-in or waitlist entry created in that hour was FILED under yesterday. The rest of the app's UTC handling is CORRECT and must not be swept up with it — a date-only string parses as UTC midnight, so `new Date(dateStr).getUTCDay()` is the real weekday (ten sites) and `Date.parse` on two such strings is an exact multiple of 86400000, which is what makes `dayDiff` immune to DST where local midnights would make one spring day 23 hours and round to 0. `addDays` is WeekView's ex-private helper, moved out because the four date-navigation sites hand-rolled `setDate(getDate()+n)` — UTC midnight in, LOCAL components out — and returned the SAME date on the spring-forward day: `2026-03-29 → next` was `2026-03-29`, i.e. forward navigation was dead once a year. The correct implementation was the hidden one; the public behaviour was the broken copy (tests/day.test.js, TZ-deterministic via `node:process`)

- **submitGuard.js** — v17.16.0 — the commit-once guard: **one open of a form produces at most ONE create**. `READY`/`DISPATCHED` + `mayDispatch(state)`, held in a ref and checked in FOUR places — `doSave`/`doSaveWalkin` and their button handlers `save`/`saveWalkin`, because those wrappers can raise the kitchen-busy confirm and RETURN before the guarded function is reached, so a second tap produced a stray dialog for a booking already written (`/code-review`). Fixes CT-2C-01, the most reachable defect the v17.15.7 crash test found: two taps 200ms apart produced two confirmed reservations on two tables, three synchronous taps three — with every safeguard correctly satisfied, because each tap is a fresh `doSave` minting a fresh `genId()` and nothing tied the writes together. **`disabled` on the button is NOT the fix and the reason generalises**: both save paths dispatch and then call `setShowForm(false)`, but `Overlay` self-animates its close through `ModalPresence`, so the subtree — Save button included — stays mounted and hit-testable for `EXIT_MS` (240+20=260ms). A second tap at 200ms lands on a live button inside a modal that is already closing, so anything depending on a re-render is racing the exit animation. Three sequencing rules, all three pinned in tests/submit-guard.test.js against a sabotaged build: CHECK at the top of the handler, before validation (after it, a double-tap on a valid draft still passes); ARM only after the write actually dispatched, on the line that closes the form (before it, a throw strands the form open and unsavable; on a validation return, the user cannot correct a field and retry); RESET on OPEN only — `openForm`/`openWalkin`, which are each their surface's single door **and already the one place that snapshots the unsaved-changes baseline**, so the guard rides a mechanism the repo already keeps in step. There is deliberately NO time window: it would have to outlast the exit animation and undercut a plausible second booking, and that number stops guarding on a slow frame. `mayDispatch` is `!== DISPATCHED` rather than `=== READY` so it FAILS OPEN — a Save button that silently does nothing is worse than one that works twice, since the first is invisible and needs a reload while the second leaves a duplicate somebody can delete

- **clamp.js** — v17.10.2 — `clampStep(n,def,min,max,step)`, the settings-sanitiser primitive: snap to the field's step, fall back to `def` when the value is not a number, hold it inside the bounds. It lived VERBATIM in `useBookingDefaults.js` and `useGeneralSettings.js`, and the second copy carried the comment "NaN check AFTER the round (see useBookingDefaults for the why)" — code that knows it is a copy and points at the original instead of importing it. The ordering is load-bearing: `Number(n)` NaN survives `Math.round(n/step)*step`, so a finite check placed BEFORE the round lets NaN escape through `Math.max`/`Math.min` and a stepper renders "NaN min" and writes it back. **`null` and `""` are NOT absent** — `Number()` makes both `0`, which is finite, so they clamp to `min` rather than taking `def`; unreachable from Firebase (RTDB cannot store null — writing it deletes the key) but pinned in tests/clamp.test.js so the next person to "fix" the guard sees it first

- **keyboard.js** — v17.10.2 — `isTyping(el)`, the guard every key handler asks first: is focus inside something the user is typing into. Lived twice (`useKeyboardShortcuts.js`, `ManualModal.jsx`); a drift between two copies costs a service in the subtlest way — a key correctly ignored while typing on one surface and silently swallowing a keystroke on the other. `SELECT` is in the list although you do not type into a dropdown: a `<select>` handles its own letter keys for type-ahead, so treating it as a text field is what stops the app's single-letter shortcuts from stealing them

- **serviceWorker.js** — v17.10.1 — the app's half of the offline shell (`public/sw.js` is the worker). Owns the `mgt-sw` key, its reader/writer and `applyServiceWorker()` in ONE file (the LoginScreen restaurant-name precedent). **Per-device localStorage ONLY, never `settings/users/{uid}`**: clearing site data is the last-resort escape from a bad worker, and a synced flag would come straight back down and re-enable what the user just escaped. - **customers.js** — phone-identity layer (v16.0.0) — normalizePhone/formatPhone/matchCustomerByPhone (VERBATIM from the WA sandbox's whatsapp.js; complementarity contract: the WA module imports these from HERE on merge) + isNoShow (flag OR legacy history entry — zero-migration backfill) + v17.10.0 `guestId`, the SECOND identity key — minted only when a human picks an existing phone-less guest from the name dropdown, so nothing merges by accident — with `identityKey` (phone if real, else guestId), `matchesIdentity`/`matchCustomerFor` (a UNION of the two keys, never a fallback: a guest who later supplies a number has bookings carrying one key or both, and matching either keeps them one person — **but v17.16.5 (CT-2B-05) carves one case out of the union: a booking carrying its OWN real phone is never reached through a `guestId`.** `customerIndex` keys on the phone FIRST, so after a mis-join such a booking is already DISPLAYED as a different customer with a different number, while the union still let "Delete customer & all data" on one row anonymise it. The list said two people and the delete acted on one, and a wrong join is invisible, so nobody could know. Three details: `hasRealPhone` and not `b.phone`, because the form seeds the field with the dial prefix and reading `"+34"` as a different number would exclude the customer's own bookings from their own delete; the exclusion needs a phone on BOTH sides, or a row keyed by `guestId` alone stops reaching anything; and the phone-LESS bookings in the group are still taken, deliberately — for a CORRECT join they are the customer, and matching only a booking's own key would strand a genuinely phone-less guest's history on every correct join to guard against the rare wrong one. **And the predicate is shared** (/code-review): `matchCustomerFor` filters with it, so the same exclusion moves the booking form's "Regular · N past visits" and no-show chips — the right answer, and the one `customerIndex` and `noShowMap` already gave, so the three agree now where the chips and the delete were the two that did not. Edit `matchesIdentity` for a delete reason and you are editing what the form asserts about a customer) + `stampGuestSeed` (the back-stamp that writes a minted id onto the booking it came from — pure, idempotent, refuses to re-home a booking already in another group; it lives in `lib/` and not in App because it decides a PERMANENT link nothing can unpick) + **`resolveGuestId` (v17.16.6, CT-2B-08) — the OTHER half of that same decision, and for six versions it was missing.** `stampGuestSeed` answers "does the seed take this id" and nothing answered "does the draft keep it": a seed joined between the name-dropdown pick and the Save (by another device, through a DIFFERENT booking of that guest — the only way the ids can differ, since the mint is deterministic in the seed's id) was correctly left alone, and the new booking was still written with the id minted at pick time, landing in a group of ONE beside the group the operator meant to join. **The seed wins**, because it is the existing group and this booking is the newcomer asking to be let in; adopting the other way would re-home a booking already joined to somebody, which is what `stampGuestSeed`'s guard exists to prevent. Called inside `doSave`'s `buildNext` and NOT baked into `nb` — `nb` is built once so a replayed write cannot duplicate the booking, while this must re-read a `prev` that may have acquired the id since the first attempt. No seed (an edit, an ordinary phone booking, `bookAgain` on a booking that already had an id) and a seed no longer in the list are the same case: there is nothing to reconcile, so the draft's own value stands + customerIndex/searchCustomers/noShowMap, keyed on `identityKey` since v17.10.0 — a JOINED guest is a customer in Settings → Customers with a `key`/`guestId` on the entry and `phone: ""`; an UNJOINED phone-less booking still has no identity and is still skipped. Whoever adds a consumer: `searchGuestsByName` must skip index entries with no phone (it rebuilds the guest tier itself, from the bookings, and would otherwise emit each joined guest twice), and anything keying UI state on `c.phone` collapses every guest row onto one `""` key. **But the index is NOT keyed on `identityKey` alone** (/code-review): `guestPhoneAlias` folds a guest group into the phone it LATER acquired, because "phone if real, else guestId" is the very fallback `matchCustomerFor` warns splits a guest at the moment they become identifiable. It shipped that way for one commit and made one person two rows with half the visits each — and "Delete customer & all data" cleaned only the half you clicked. A `guestId` seen with two phones takes the lexicographically smallest: arbitrary, but DETERMINISTIC, so every device agrees who a customer is. Hence `matchesIdentity` takes `guestIds` (plural), and `noShowMap` mirrors each total onto the aliased id so `nsMap[identityKey(b)]` resolves for either spelling + v16.4.0 searchGuestsByName (booking-form NAME autocomplete). Customers are DERIVED from bookings — no separate collection. **v17.10.0 adds the SECOND identity key, `guestId`** — `identityKey(b)` (phone if real, else guestId) and `matchCustomerFor({phone,guestId},…)`, of which `matchCustomerByPhone` is now a thin alias keeping its exact name/signature for the WA contract. The two keys are UNIONED, never a fallback: a guest who books three times with no phone and then gives one carries bookings with only a guestId and bookings with both, and "phone if present, else guestId" would split them at exactly the moment they became easiest to identify. `searchGuestsByName`'s never-merge rule is UNCHANGED in substance — phone-less bookings still never merge on name, because nothing in the data separates two guests called Maria — but rows sharing a `guestId` now collapse into one, and that id is only ever minted by a human picking an existing phone-less guest from that dropdown (or Book Again on one). Merging is opt-in, per guest, by someone who could see both bookings. `noShowMap` is keyed on `identityKey` for the same reason; read it as `nsMap[identityKey(b)] || 0`.
