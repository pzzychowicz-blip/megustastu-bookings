The boot script stays inline with its CSP hash.
- **wa-connect/** — the `/wa-connect` page, a second document built by its own config (`vite.wa-connect.config.js`; why at `waConnectPage()` in `vite.config.js`) with its own CSP. Shares `firebase.js`, the stylesheet and the sign-in, nothing else. ## Architecture decisions

- **Hook vs component.** A hook is stateful logic the parent renders with (plumbing moves, rendering stays); a component is a UI unit with its own complexity (everything moves). Reasoning: `REFACTOR_LOG.md` Phase D vs E.
- **Controlled components** (WalkinForm, BookingFormModal): form state lives in the parent; the component fires named callbacks. Pass setters directly only for the draft itself (`setForm` / `setDraft`). Sub-modals stay in the parent's tree, so the z-stack stays predictable.
- **Optimizer scope** (D3 Option A, permanent): the `autoOptimizer` thermostat lives in `useAutoOptimizer` (off at 15:00, on at the new day). The banner stack and its state stay in `BookingApp`: they reach into form, view and persistence, and `flash()` has many call sites.
- **`confirmKitchen` is shared**: owned by BookingApp, raised by `doSave` and by `useWalkin`'s `saveWalkin` (passed in as args; same pattern for `setWriteWarning` between `usePersistence` and `useReminders`).
- **Auth shell**: `App()` is the gate (`onAuthStateChanged` → `<LoginScreen/>` or `<BookingApp/>`). Hooks that need the authed shell mount in `BookingApp`.

## Critical patterns

### Operating hours — live module bindings
`OPEN` / `CLOSE` / `GRID_CLOSE` / `QUARTER_HOURS` (`constants.js`) are `let` exports reassigned **only** by the module's own setters (`setActiveDayHours(date)`, `setWeekHours(week)`); as live ESM bindings, every importer sees the new values with no signature change. `useOperatingHours` calls the setter per snapshot AND sets state so BookingApp repaints. **Never capture them into a module-scope local** (it breaks the binding); read at call or render time.
- **Bounds**: open 6–22, close (open+1)–25 (`clampHours`, through `sanitizeDay`); `GRID_CLOSE = close + 1`, unclamped, so a past-midnight close extends the grid (labels wrap `% 24`). **No booking may START after midnight**: close caps at 25, and `findTimes` / `findKitchenFriendlyTimes` guard `m < 24*60`. Time inputs cap `max` at `"23:59"` (`<input type=time>` rejects "24:00").
- **Per weekday + closed days**: `settings/operatingHours` is `{days:{"0".."6"}}` (UTC weekday; a legacy flat pair reads as uniform via `sanitizeWeek`). **`hoursFor(date)` is THE accessor for any date** (`{open, close, gridClose, closed}`); the date-carrying pure functions read it, so a booking on another date stays correct. `useOperatingHours(viewDate)` calls `setActiveDayHours` DURING render (module mutation, no setState), so children read the view day's hours in the same paint. `weekRange()` (min open…max close over open days) clamps the shift split; the optimizer cutoff is decoupled (0–24).
- **Special days**: `exceptions` beside `days` (`lib/special-days.js`); `hoursFor` checks `HOUR_EXCEPTIONS` BEFORE the weekday and answers `special: true` and the `note`. **A new reader of a date's hours asks `hoursFor(date)`, never `WEEK_HOURS[weekday]`**, or it misses them. `weekRange()` stays weekday-only. The memoised views repaint on `hoursSig`, the hook's `{week, exceptions}` state, so a special day saved for the viewed date repaints. Bookings already made are kept when a special day is saved over them (Patryk).
- **`extendActiveGrid(endMins)`** stretches the ACTIVE day's `GRID_CLOSE` / `QUARTER_HOURS` to the viewed day's latest booking end (capped at 26). It is called in render straight AFTER `useOperatingHours(viewDate)`, whose `setActiveDayHours` resets the bindings, so the order is load-bearing (`tests/grid-extend.test.js`). **Display only**: `hoursFor` does not move, and **a STORED default must not read the live binding** (BlockModal's default "to" reads `hoursFor(date).gridClose`, or it opened blank at "24:00").

### Layout config — live module bindings
The layout bindings (`ALL_TABLES`, `INDOOR`, `OUTDOOR`, `TIMELINE_TABLES`, `TOTAL_SEATS`, `ZONE_OF`, `TABLE_GROUPS`, `KITCHEN_TABLE_LIMIT`, `VALID_COMBOS`, `CLUSTERS`, `PRIORITIES`, `PICK_RULES`) are `let` exports reassigned only by `setLayout(cfg)` (via the pure `buildLayout`), seeded from `DEFAULT_LAYOUT` at the BOTTOM of `constants.js` (TDZ-safe). `useLayout` sets them per snapshot and repaints. Same two rules as hours: never capture into a module local, and **editing `DEFAULT_LAYOUT` under HMR needs a full reload**.
- **Combos are DERIVED**: every contiguous run (≥2) of a join group (cap from `comboCaps[comboKey(run)]` or the sum), then `megaCombos`. A table belongs to ONE join group (`sanitizeLayout`, first wins).
- **`DEFAULT_LAYOUT` is the restaurant's renumbered layout** (tables 1–13; `tests/layout-default.test.js`: 13 tables, 28 seats, 40 combos). It is only what a database with no layout node gets. The pickers' grouping is `makeTableGroups()` for every layout.
- **Pick rules** (`settings/layout.pickRules`, live as `PICK_RULES`): two tables of a pair may be hand-picked together only with every table of `need`, unless the set holds a whole declared combo with both. `pickBlockedBy(ids)` is the one question; a hand picker takes `togglePick(sel, id, needed)` → `{tables}` or `{refuse}` (`pickRefusal`, `unpickRefusal`). **A new hand picker takes `togglePick` too and never names a table id in code** (four hard-coded ids switched off unnoticed at the renumbering). Absent object = the default's rule; present = what it holds (`normalizePickRules`).
- **Rename a table = remap every reference** (tables, join groups, `comboCaps` keys, `megaCombos.ids`, the `priorities` refs, the pick rules), so combos and rules survive; remove drops only the table and what referenced it.
- **Optimizer priorities** (`PRIORITIES`, from `settings/layout.priorities`; field meanings at `DEFAULT_LAYOUT.priorities`) drive `_comboPri`, `_indoorPri`, `findBest`, `optimise`'s swap rules and `isMixedLarge`. **An ABSENT `priorities` object seeds from the default; a PRESENT one treats each missing field as EMPTY**, because RTDB drops empty arrays (`v` keeps an emptied config present). The editor always writes the full shape. Refresh devices before tuning (an old device's save wipes the field).

### Customer layer — derived from bookings
Customers are **DERIVED from bookings by normalized phone** (`lib/customers.js`); there is no `customers` collection. The phone primitives (`normalizePhone`, `formatPhone`, `matchCustomerByPhone`) are the ONE phone-identity source: WhatsApp code imports them, never a copy. `isNoShow(b)`: still cancelled, and the `noShow` flag or the latest of `"no show"` / `"no-show cleared"` in history. Delete customer anonymises their bookings (permanent; armed confirm), and the empty-array write guard may refuse it when they are the whole database — safety wins.
- **`guestId`, identity for a guest with no phone**: `"g" + <seed booking id>`, derived so two devices mint the SAME id. Minted only when a human asserts identity (picking a phone-less guest from the NAME dropdown, Book Again), and the draft's `guestId` + `guestSeed` are written by ONE `saveBookings` (`stampGuestSeed`; its `!b.guestId` guard keeps a retry idempotent and never re-homes a booking). `guestSeed` is never persisted.
- **`customerIndex` is keyed on `identityKey`**, so a JOINED guest is a customer (`phone: ""`); an unjoined phone-less booking has no identity (the never-merge rule). Consumers must handle `rawPhone: ""` — never key UI state on `c.phone`.
- **Guest tags live on bookings**: a booking may carry a STATEMENT (`guestTags`, `guestTagsAt`); the guest has their NEWEST statement (id breaks a tie). Patryk chose this over a customers node. Four rules, each from a way a simpler shape loses a tag:
  - **Read through `guestTagMap(bookings)` + `guestTagsOf(b, map)`**, never `b.guestTags` (the statement is usually on another booking).
  - **The form holds TAPS** (`guestTagEdits`), never the set: shown and saved is `editTagIds(guestTagBase(list, id, ident), edits)`. A held set is overwritten by the next phone typed and replays stale. `saveGuestTags` runs on `prev` inside both transforms.
  - **A new stamp is `max(now, newest + 1)`**, or a slow clock's change is saved and never seen.
  - **A booking that LEAVES its guest hands its statement on** (`rehomeGuestTags`): any path that drops a booking or changes its phone or `guestId` goes through it.
  - The history line never names a guest tag (`/activity` is append-only, beyond Delete customer's reach); occasion tags (`tags`) are named. Delete customer is `anonymizeBooking`, clearing both kinds.
  - **Six surfaces show `bookingTags(b, guestTags, tagList)`** from ONE `guestTagMap` memo in App, passed as a stable prop; `tests/guest-tags.test.js` fails a component reading `b.guestTags`. The walk-in form has no tags (Patryk).

### Waitlist active matching
`waitAvail` is **state computed by an effect**, not a render derivation (the `trialFits` scans are heavy), keyed on `nowQuarter`, never the raw 15s tick. Per entry: `prefTime` first, else a 15-minute scan **within ±90 min** of the wanted time.
- **Entries are matched SEQUENTIALLY, first come first served** (`createdAt` ascending): each party that fits is appended to `holds` as a `_locked` booking the next one scans against, or several parties are offered the same table at the same minute. `_locked` is load-bearing (`applyOpt` copies a locked booking through). A budget-skipped entry's previous answer is held too.
- Book prefills the form + `pendingWaitlistRef`; the new-booking path HOLDS the entry (hidden, still stored) and removes it when the booking lands, so a booking discarded from the "Couldn't save" banner does not lose its party.

### The module registry — what this restaurant HAS
`lib/modules.js` + `settings/admin.modules`: `vouchers` (default on) and `whatsapp` (default off).
- **A module is not a capability**: `roles.js` answers whether THIS PERSON may do it; this answers whether the restaurant HAS it. **`moduleOn` is checked FIRST and `can` never runs** for an off module, so it is hidden from everybody, admins included; the other order would let a grant re-open a switched-off feature. `visibleTabs(can, hasModule)` encodes it.
- **Absence resolves to each module's `defaultEnabled`**, never to false (an absent `modules` is production on deploy day); a stored value counts only as `=== true` / `=== false`; an unknown id is dropped and `moduleOn` returns FALSE for it (a typo hides a surface visibly, rather than leaving one open).
- **Off means every surface** (Patryk). Vouchers have seven gates; three sit at FUNNELS, not renders: `voucherToAsk` (`voucherDue`) for the form's save and `updateStatus`; `voucherToRestore` (`voucherReturnDue`) at `updateStatus`, the form AND `doCancelBooking` (cancel bypasses `updateStatus`'s gate), behind the SAME `redeemAskedRef` as `voucherToAsk` (a status change goes into completed or out of it, so the two prompts are never both pending, and a second ref would be one more thing to keep in step); the `unsettledBookings` memo feeds both the strip and `notifAnnounce`. **The restore gate is "is this booking LEAVING completed"**, never a list of target statuses. `settleVoucherBack` writes the booking first and moves money only if it landed. **Money never moves as a side effect of a status tap, and never silently stays put.** Hidden is not deleted. The Admin tab names open vouchers before the switch moves (`hideWarning`) and then refuses nothing.
- **WhatsApp has TWO flags; a new surface picks the right one.** `whatsappOn` (the module, restaurant DATA) gates everything a restaurant reaches: the toolbar button, `I`, the Settings tab, the listeners. `WA_SANDBOX` (build-time) gates only the SIMULATOR. A runtime switch needs the gate in the listeners' dep arrays, the Settings tab branches on `cur` (never the raw `tab`), and the templates seed is prevented by the module shipping off. The inbox takes no capability (service work; Patryk).
- **Multi-tenancy is this and nothing more**: one project per restaurant gives each its own `settings/admin`.
- **Integrations holds no secret and says so**: root `.read` is `auth != null` and cascades down, so any key in RTDB is readable by every account. Keys live in deployment env vars; the panel states where, and never claims to know whether one is set.

### Per-user preferences — `settings/users/{uid}/prefs`
Theme, reduce animations, Plan zoom & pan, lock navigation, split view and plan availability follow the ACCOUNT (`useUserPrefs.js`).
- **Device fallback is the migration**: each keeps its `localStorage` initializer; once per uid after `prefsLoaded`, a saved field overrides local state and an unsaved one is seeded from this device. **Tri-state**: `null` means never chosen; a sanitize returning `false` for absent would reset every device.
- **`theme: "auto"`** (Automatic dark mode) is stored explicitly, since `null` would be filled by the next device's explicit value. It reads as `undefined` at every theme site, so the boot script and its CSP hash are untouched (`tests/prefs.test.js` runs the real script). An unset `themePref` is never seeded up.
- **The booleans come from `PREF_SPEC`** (key and default direction once): only the non-default value is stored, `"whenOn"` the default-off shape, `"whenOff"` default-on.
- `<BookingApp uid={user.uid} key={user.uid} />`: the **key** remounts on an account switch. Rules deploy app-first (`database.rules.README.md`).

### Separation between bookings — the turnaround buffer
Minutes a table stays unavailable after a party's end; off by default (`TURN_BUFFER` 0).
- **Pad every END — the stored slot's and the candidate window's — never a start**, so the gap is exactly the buffer in both directions (`bookEnd(b)`, `padEnd(e)`).
- **Placement only** (Patryk): the placement functions and the UI busy sets (`ManualModal`, `WalkinForm`, `pickedRefusal`). **`verifyClean` / `findConflicts` / `checkInefficent` do NOT use it**, so turning it on never flags or reshuffles a day already booked back-to-back. `getBlockSlots` and `applySeatedShift` are unbuffered.
- Drawn as a separate faint tail on the Timeline (not a longer block: `liveBarDur` gates the chips) and a dashed outline in Plan. Both views take a **scalar `turnBuffer` prop**, never the live binding (`React.memo` cannot see one).

### Optimizer cutoffs
15:00 turns `autoOptimizer` off for today; midnight turns it on. Seated bookings are never reshuffled (`trialFits` / `applyOpt`); walk-ins are `_manual` + `_locked`.

### `bookingsAfterAction` is the central save path
Every booking mutation goes through `bookingsAfterAction(bookings, viewDate, tableBlocks, savedId, isNew, autoOptimizer)` (optimizer reshuffle, seated shift); a direct `saveBookings(arr)` risks an inconsistent schedule. **ONE exception: `undoLastAction`** (`planUndo`, `lib/delete-undo.js`) restores verbatim, because `optimizerActiveFor` is always true for a future date and the reshuffle would re-apply the moves Undo reversed. The reconciliation effect resolves any conflict. Never add the call back.

### The fixed shell — `shellFixed`
Normally `<body>` scrolls. `shellFixed` makes the outer div a `100dvh` overflow-hidden flex column with pinned header rows and ONE `flex:1; minHeight:0; overflowY:auto` region; a separate effect sets `body.overflow = hidden` (separate because the mount effect sits above `navLocked`'s declaration, a TDZ). **One mechanism for Lock navigation AND Split View** (`navLocked || !!split`), never a second layout; both default off. Split View implies a pinned nav (two panes need a definite height), and `SlideView` needs `fill`.

### Split View
Two of Timeline / List / Plan at once, per device; tablet and up (`winW >= 600`, enforced by `readSplit` and an effect). State `split = {a, b, dir, ratio}` or `null`, persisted only through `applySplit`; `readSplit` validates HARD and returns `null` on anything odd. The master toggle defaults ON (stores only `"0"`); the gesture is inert while it is off.
- **The same view can never fill both panes**: the timeline, list and follow-now state are singletons in App and two instances would fight.
- All three views are built unconditionally (`viewEl`). The keyboard follows the focused pane (`view: activeView`). **`activeView` must stay declared ABOVE the `useKeyboardShortcuts` call** (a TDZ blanked the app once).

### Unsaved-changes guard — every drafting surface registers
Six surfaces hold drafts: the booking form, the walk-in form, `ManualModal`'s picks, `ReminderEditor`, `BlockModal` and Settings' text boxes. Each snapshots its opening draft and diffs (`sameDraft`, `lib/drafts.js`); **an untouched surface closes silently** (a confirm on every Cancel trains people to tap through it).
- **`openForm` is the ONE door that sets the booking form's baseline** (`openWalkin` for the walk-in); any other `setForm` is an edit. Baselines are STATE (read in render).
- A child that owns its draft reports `onDirty` up with an unmount cleanup `onDirty(false)`, or a closed modal leaves `beforeunload` armed.
- **Flatten a nested draft before diffing** (`flatReminder()`): `sameDraft` falls back to key-order-sensitive `JSON.stringify`. Settings aggregates through `reportDirty(id, on)` backed by a **Set of ids, not a counter**; its reset lives in `closeSettings()`. Steppers and toggles commit per tap and are unguarded.
- **A new drafting surface needs three things**: a baseline at its open site, its mount-site `onClose` pointed at a `requestClose*`, and that `requestClose*` named in `escapeAction` for its modal id (`tests/modal-stack.test.js` fails an id with none). Closes that already represent a decision keep the raw setter.

### `formRef.current` vs `form`
Event handlers and async callbacks read `formRef.current` (always fresh), not `form`; the mirror is kept by an effect on `[form]`.

### The app's name and the restaurant's name
The APP is MGT Bookings (`APP_NAME`, `src/lib/constants.js`); the RESTAURANT is configurable (`settings/general.restaurantName`, seeded from the tenant's `profile.name`). **Never compose one out of the other** (a FALLBACK from restaurant name to app name is fine). Four hand-typed copies of the app's name had drifted with no gate able to see it. The seven copies that cannot import the constant (`index.html` ×3, the manifest ×2, `public/sw.js` ×2) are pinned by site AND count in `tests/stylesheet.test.js`, because the first guard's prose claimed coverage it did not have: count, don't claim.

## The five write guards — the mechanics

The root `CLAUDE.md` keeps the five guards as rules; this is how each works. Code: `src/hooks/usePersistence.js` and its pure core `src/lib/write-path.js`.

1. **Loaded + non-empty** — the root's pattern.
2. **Freshness / resync gate.** A 10s heartbeat bumps `lastBeatRef`; a gap `> STALE_GAP_MS` (90s, ≫ the heartbeat) means the event loop froze (a sleeping laptop wrote a stale snapshot over a night of bookings). The gap is checked **at write time**, before any setState. `markStale()` sets `staleRef` and the banner; `resync()` force-pulls `bookings` + `tableBlocks` with `get()`, only while `isConnectedRef` (an offline `get()` serves the cache), and `gapTrip()` resets that ref on wake. Cleared by a live `onValue` or a successful resync; network blips never trip it.
3. **Server-side compare-and-swap.** Every write proves it was based on what it overwrites (newer-stamp-wins was last-writer-wins under clock skew).
   - **Per-child nodes** (`bookings`, `vouchers`, `roles`, `invites`): `stampForWrite` writes `updatedAt` (monotonic, above the last-seen server value) plus `baseUpdatedAt`; the rule requires `baseUpdatedAt === stored updatedAt`, and `0` on a create (so a stale edit cannot resurrect a deleted booking). `baseUpdatedAt` is per-write metadata, not in `sanitize`.
   - **Whole-node collections** (seventeen pairs): `lib/revGuard.js`, a sibling `<name>Rev` and an atomic `update({node, nodeRev: base+1})`; the rule accepts only +1. Rev refs advance optimistically.
   - **No root `.write`**: write permission cascades down and cannot be revoked lower, and the rev CAS sits in `.write` because `.validate` is not evaluated on a delete. **No whole-node `bookings` write anywhere.**
   - **Per-field `.validate` on a booking** means "if present, the right shape" (`sanitize` fills gaps on read). `date` and `status` are pinned as `matches(...) || newData.val() === data.val()`, so a stored value carried through unchanged is always allowed; the date regex is an optional group (`""` is a shape `sanitize` emits). `time` is unpinned on purpose: `isReadableTime` accepts `"9:30"`, `"13:00:00"` and `":"`, so a pinned format would refuse writes to data that already exists.
   - **StrictMode dedupe**: `lastPatchSigRef` drops a double dispatch only with the same content AND `baseUpdatedAt` within 2s (pinned). A rejected write recovers through `.catch → markStale → resync → drainPending`. Deploy app first, rules second.
4. **Save feedback + retry.** `saveBookings` / `saveBlocks` return a boolean (dispatched), and **every success UI is gated on it**, so a refused write is never shown as saved. The red banner is for hard failures only.
   - A held or rejected **function-form, non-silent** write parks in `pendingRetriesRef`, replays on fresh data up to `MAX_RETRIES` (3), then waits in `parkedRef` for Retry / Discard. **Value-form and silent writes never queue** (replaying a precomputed array re-writes stale data). A held write applies locally at once, and `drainPending()` runs from `resync()` and the live `onValue` so a snapshot cannot wipe it. `doSave` uses the function form: intent captured once, `buildNext(prev)` replayed, `applyBase` filters `newId` so a replay cannot duplicate.
   - **The write's `report`** (`saveBookings`' third argument) rides with the queued item: `onLanded()` once when the server has it (a side effect that must not outlive its write goes there, e.g. "Repeat weekly"'s rule); `onDiscarded()` once for a write that will never land (`tellDiscarded`); never both, and a closed tab hears neither, so anything done at the dispatch must be something a reload undoes. `replayRefusal(prev)` is asked before each replay (`replayOutcome`). **Every change to ONE booking passes `goneReport(id)`** (`goneRefusal`), which also sets `subject` for the parked banner (`describeWrite`); `tests/retry-report.test.js` lists the callers, so a new single-booking writer joins it. A REJECTED patch clears the dedupe signature, or an identical replay is skipped.
5. **Per-booking storage + diff-write.** `/bookings/{id}`, so devices editing different bookings write disjoint paths. A save computes from the `bookingsRef` mirror (never inside a setState updater) and sends a multi-path `update()` of changed children plus `{id: null}`; an empty diff writes nothing, and `bookingChanged` ignores `updatedAt`. A legacy array node migrates once (`migratedRef`; `arrayShapeRef` holds per-child writes until the keyed shape echoes): old keys are read off the SNAPSHOT (so a row `sanitizeAll` dropped is still cleared), and the keyed rows are assigned OVER the nulls (so an id equal to an old index is not deleted by the patch writing it).

**Post-sync reconciliation** (`lib/reconcile.js`). Two devices that booked offline can overlap once synced. An effect finds `dirtyDates` (≥ today, failing `verifyClean`; a clean sync writes nothing) and makes one **silent** function-form save: a full reshuffle where `optimizerActiveFor`, else relocating only the newest non-locked conflicting booking (`updatedAt` desc, id tiebreak: deterministic across devices) via `forceReassign`, at most 20 passes. `_locked` bookings never move. Gated on `!resyncing` and **`firstLoadCount`**, never `loadBannerShown` (it auto-hides after 6s). It compares content, never identity (`bookingsAfterAction` returns its input when nothing moved).

## Lessons carried over

- **StrictMode mounted ref**: set `mounted.current = true` INSIDE the subscription effect, not only in `useRef`.
- **Read computed styles before iterating on visual feedback**: a mismatch usually has one structural cause.
- **Preserve inline styles on refactor**: check every declaration survives a split, and put a specific side AFTER a spread that holds a `margin` shorthand.
- **Grep unfamiliar atoms before use** (`mkInp` / `mkBtn` return style objects here, unlike Scheduling).

## Gotchas and constraints

Each row keeps its title (code comments and tests cite them) and its rule, with the reason in a sentence.

| Issue | Constraint |
