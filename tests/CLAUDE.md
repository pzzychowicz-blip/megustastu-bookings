## The suite

A Vitest suite — `ls tests/*.test.js` lists the files and `npm test` gives the live count. Neither is copied into these docs any more: every hand-kept copy of the list or the number drifted, so measure instead. Run the BUILD first, or one test is skipped — `tests/csp.test.js` has one `it.runIf` on the built `index.html`. CI gates build + test + **lint (0 errors, hard)** + **`npm run check:style`** on every PR via `.github/workflows/ci.yml`. **No DOM or interaction tests, and deliberately no jsdom / testing-library** — UI verification is AST audits + manual DEV QA. `tests/error-boundary.test.js` (v17.16.0) is the ONE place a component is exercised, and only because an error boundary's whole decision is a static method plus a `render()` branching on one state field: it constructs the class directly and reads the returned element tree (React elements are plain objects), mounting nothing. That is the bar for repeating the trick — not a licence to test components generally.

**`tests/rules/database-rules.test.js` runs somewhere else on purpose**: it drives a LOCAL Firebase RTDB emulator against the real `database.rules.json` (`npm run test:rules`; needs `brew install openjdk` + a global `firebase-tools`). It is EXCLUDED from `npm test` in `vite.config.js`, because the `verify` job that runs `npm test` has no JVM — it now runs in CI, but in a second job of its own (`rules`), so the exclusion is what keeps the two apart rather than what keeps it off CI. See the gotcha below. Until it existed, everything the app asserts about SERVER-SIDE write safety (the per-`$id` CAS that closed the 2026-07-05 incident, the sixteen `<name>Rev` pairs (counted from `database.rules.json`, 2026-09-11), the `auth != null` boundary) was verified by prose in the root CLAUDE.md and by nothing else. Its fourth group is marked `PROBE:` and asserts what the rules **permit** — findings to rank, not approvals; never make one pass by weakening its assertion. **Three PROBEs became closed assertions in v17.16.7** (whole-node `/bookings` deletion, a rev-bypassing `remove()`, arbitrary top-level nodes) — inverted with the rules, which is what the convention exists to force, and the third of those was closed as a side effect nobody aimed at. `database.rules.README.md` holds the setup, the two independent no-real-project guarantees, and the rule that a new rev pair joins `PAIRS` in the same PR that adds it to the rules.

**The rule v17.8.0 added: logic that decides something the restaurant acts on does not live in a `useEffect`.** `placeWaitlist` and `presenceState` were both extracted for that reason — a double-booking fix had shipped on "it looked right in DEV". If a behaviour is worth a REFACTOR_LOG paragraph it is worth being reachable by a test: put the pure core in `lib/`, leave the hook its subscription, refs and setState.

**Fixture trap:** `ALL_TABLES` holds `{id, capacity}` OBJECTS, not ids. A "fill every table" fixture built straight from it silently occupies nothing, and the failures point at the code. Use `ALL_TABLES.map(t => t.id)`.

**`tests/stylesheet.test.js` guards `src/index.css`** (`index.html`'s `<style>` until v17.15.1) — a stylesheet has no syntax errors, only rules that silently don't exist (v17.8.0 lost `.mgt-press:active` to a stray `*/` and nothing noticed). It checks comment hygiene, brace balance, a CRITICAL_SELECTORS list, and — added after the same defect recurred one scope deeper — **loose prose inside a DECLARATION block**, which eats the declaration *after* it rather than the rule after it. That version made `--tbl-out-rgb` resolve to empty, which would have rendered nine table badges transparent, while every existing test passed. Entry criterion for CRITICAL_SELECTORS: does the rule fail SILENTLY when missing?

**A regex reading of CSS is not what the browser sees.** `tests/contrast.test.js` extracts tokens with a regex and would happily measure a declaration the browser has thrown away, so parse validity needs its OWN guard and cannot be inferred from a token-reading test passing.

## Gotchas

| Issue | Constraint |
|---|---|
| A source-scanning test that reads RAW | The tool to prevent it has existed since v17.13.0 (`scripts/strip-comments.mjs`) and **two of thirteen** source-scanning tests were using it — so the convention was real, unenforced, and wrong in eleven places. v18.0.0 phase 4 converted them (the figures here are MEASURED: the first write-up said two of eleven and nine, which was the count taken before the new guard found its last two offenders and never re-taken — the drift this very row is about, in the row itself) and added `tests/test-hygiene.test.js`, which fails the build when a test greps JS/JSX and does not import the stripper. **The measurement that settles why**: `settings-tabs.test.js` reads `useKeyboardShortcuts.js` for the `visibleTabs(` call, and the comment above that call quotes `visibleTabs(can)` — raw, the first match's arguments are `"can"`; stripped, `"K.can,K.hasModule"`. So the raw read answers with the SENTENCE ABOUT THE CALL, which would fail the build for a correct consumer and — the reason this is a guard and not a note — would let a `toContain("can")` assertion PASS FOREVER over a consumer that had dropped the gate, because the comment satisfies it. The guard found two more offenders on its first run (`contrast.test.js`, whose whole subject is colour literals in files full of prose about colour literals, and `stylesheet.test.js`). **Stripping is not always right, and the guard is deliberately a prompt rather than a proof**: it checks the file IMPORTS the stripper, not that every read uses it, because `stylesheet.test.js` reads `public/sw.js` raw on purpose — that assertion counts how often the app's name appears in the file's TEXT, header comment included, and stripping took it 3 → 2 and turned the suite red. CSS and HTML are outside it by construction: `stripComments` is the JS stripper and a bare `//` in an unquoted `url(https://…)` is not a comment |
| A guard that finds its subject BY REGEX, blinded by prose | `tests/csp.test.js` locates the boot block with `/<script>([\s\S]*?)<\/script>/`. v17.15.1 added an `index.html` comment that *mentioned* a literal script tag, so the match started inside the comment, the hash covered the wrong bytes, and the pin read as drifted. The browser was never confused — only the guard was. **Prose that names the thing a regex hunts for is indistinguishable from the thing.** Same shape one file over: the new `src/index.css` header spelled a comment-terminator literally and closed itself early, putting prose in a selector — the v17.8.0 bug, reproduced in the commit that moved the file. Both were caught only because the tests existed; both looked perfect in review |
| A test that needs a Java process | `tests/rules/**` drives the Firebase emulator, which is a **Java jar**. CI's `verify` job (`.github/workflows/ci.yml`) runs `npm test` on `ubuntu-latest` with no JVM, so a rules test left inside vitest's default include breaks **every PR**. `vite.config.js` excludes the directory, `vitest.rules.config.js` includes only it, and `npm run test:rules` wraps the run in `firebase emulators:exec`. The suite THROWS if `FIREBASE_DATABASE_EMULATOR_HOST` is unset rather than falling through to a real project, and the project id is `demo-mgt-bookings` (Firebase treats a `demo-` prefix as emulator-only) — two independent guarantees, because a silent fallback to PROD there is the one mistake in this repo that would matter exactly once. **Since 2026-09-02 CI runs it in a SECOND job** (`rules`), with `setup-java`, a pinned global `firebase-tools` and a cache for the emulator jar — parallel to `verify` rather than in series, though NOT free: measured over its first two runs (cold cache then warm), `verify` took 34s / 30s against this job's 43s / 38s, so `rules` sets the wall-clock by ~8-9s — and the emulator-jar cache did NOT close that gap, it removed the download while `setup-java` and the ~200 MB global install stayed. Deliberately not path-filtered (a filtered job reports as *skipped*, which blocks a merge outright if it is ever made a required check, and the filter would be a fifth copy of the suite's input list). **The JDK pin is `setup-java` and NOT the `/opt/homebrew/opt/openjdk/bin` prefix in the `test:rules` script**, which does not exist on `ubuntu-latest` — verified inert rather than harmful (a nonexistent `PATH` entry is skipped, so `java` resolves from further down; a bogus prefix behaves identically to none). The prefix cannot simply be dropped either: `openjdk` is keg-only, so on a Mac it is the ONLY thing that makes `java` resolve. Two halves of one pin, neither redundant. And the job must invoke `npm run test:rules` rather than the command it wraps — `npm run` is what puts `node_modules/.bin` on `PATH`, without which `emulators:exec` starts the emulator and then exits 127 on `vitest: command not found` |
| A test fixture that has to be in the FUTURE | Written as a literal, it is a time bomb with a printed fuse. `tests/reconcile.test.js` opened `const D = "2026-09-01"; // a future date` — and `dirtyDates` only looks at dates `>= today`, so on 2026-09-02 it correctly ignored the whole fixture and the suite went red on `main`, and on every branch cut from it, for a reason having nothing to do with any code change. **The first response to a red suite is to distrust the change in front of you**, which is the real cost: it took a stashed tree and a second run to establish the break was already there. Derive such a fixture from `todayStr()` through `addDays` (`lib/day.js`) — never a literal, and never a hand-rolled `setDate(getDate()+n)`, which returns the SAME date on the spring-forward day (v17.16.2). The other date literals in the suite are arithmetic fixtures (`dayDiff("2026-03-28", "2026-03-30")` is testing DST) and are correct as literals: the distinction is whether the value is compared against a LIVE clock. |
