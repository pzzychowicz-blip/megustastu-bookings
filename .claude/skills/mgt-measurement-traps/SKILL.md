# Measurement traps — MGT Bookings

Moved here from the root `CLAUDE.md`'s Gotchas table on 2026-09-17 (`/doctor`). Each row
is a reading that looked like data about the app and was really data about the
tooling. `mgt-workflow`'s rule applies — never assert what you have not measured —
and so does its corollary: check the instrument before believing the measurement.

| Issue | Constraint |
|---|---|
| Synthetic input does NOT set the UA `:active` state | Not `element.dispatchEvent`, not CDP `Input.dispatchTouchEvent` / `dispatchMouseEvent`, not `adb shell input`. Every attempt to measure a `:active` rule on the tablet read `false` — including on a plain `<button>`, which would have meant v17.8.0's universal press-scale had never worked there. It had; the measurement was of the tooling. Use CDP **`CSS.forcePseudoState`**, which answers the real question ("if this element WERE `:active`, does my rule apply?") — and always force the same state on a control that already works, as a control group. The same family of trap as v17.10.1's other two: a synthetic press also cannot arm the timeline drag and cannot raise an OS text selection. **A synthetic press is not a finger** — for anything gesture- or UA-state-shaped, the person holding the device settles in one second what an hour of instrumentation cannot |
| A perf fix aimed at a component that measures as noise | v17.15.1 planned to memoise `notifSections` on v17.15.0's measured 2.886 ms of forced layout — but v17.15.0's own early-return had already removed that, and re-measuring gave **10.9 ms/keystroke with the strip vs 10.4 ms without, and ZERO DOM mutations from it either way**. All three views cost the same ~10 ms with an identical 413 mutations, i.e. `VA` + `memo()` are working and the residual is the form plus DEV StrictMode double-rendering. **The render layer is done; measure before believing otherwise** — and note a dev-mode number roughly halves in prod |
| An accessible NAME read out of a browser-automation tree | The tree an automation tool prints is **its own summary**, not the browser's computed name, and where the two disagree the tool is usually the wrong one. Measured v17.16.3: the Timeline/List/Plan buttons carry visible text AND a `title`, and the pane's tree reported all three as "Right-click or hold to add to a split view" — recorded as a P3 finding that the app's primary nav announces as three identically-named controls. Chrome computes `name="Timeline" from=contents` and puts the `title` in `description`, exactly as the accname spec requires; a control probe (`<button title=X>Y</button>`) shows the tool reporting X where Chrome reports Y. **`title` is a name of LAST resort** — it loses to contents and to `aria-label` — so a control with visible text is already named, and "all N share one name" is the signature of a tool reading the attribute rather than computing the name. Verify with CDP `Accessibility.getPartialAXTree` (its `name.sources` names the winning source) before writing an `aria-label` that would REPLACE a working name with a paraphrase — which is the v17.15.4 Label-in-Name defect, reintroduced while believing you are fixing one. Same family as the synthetic `:active` row: the measurement was of the tooling |
| eslint's last line is not its verdict | `eslint` prints **two** trailing lines, and the wrong one reads like a clean bill: `0 errors and 1 warning potentially fixable with the --fix option` is about what `--fix` could REPAIR, while `N problems (E errors, W warnings)` is the count CI gates on. Piping through `tail -2` shows the first and hides the second. Measured v17.16.6: two consecutive commits were verified that way and reported "0 errors" while carrying a `no-control-regex` **error** that would have failed CI on the PR — found only when a later run happened to print more lines. Grep for `problems`, never `tail`. Same family as the synthetic `:active` press and the automation-tree accessible name: the reading was of the tool, not of the thing. (The `no-control-regex` hit itself is worth knowing: `undoKey`'s `SEP_RE` deliberately matches the ESC-to-US range, and the rule exists to catch the ACCIDENTAL case — it carries an inline disable with the reason, because a char loop there runs over every field of every booking through `dayBookingsSig`, and a `new RegExp` built from the same escapes is flagged identically while hiding the range from a reader.) |
| Focus / effect-cleanup behaviour measured in a DEV build | `main.jsx` renders inside `<React.StrictMode>`, which is dev-only and double-invokes every effect as setup → cleanup → setup. Anything an effect captures from GLOBAL state on the way in is therefore captured TWICE, and the second read sees the world the first pass already changed. Measured v17.16.3: `Overlay` stores `document.activeElement` to restore focus on close, and under StrictMode the second setup re-reads it AFTER the first pass has focused the dialog — so the ref ends up holding the dialog, which is detached at close, `document.contains(prev)` is false and no restore is attempted. Focus lands on `<body>`; it looks exactly like a broken restore and was filed as CT-2C-02 ("never works, on any modal"). With StrictMode removed it works in five of six attempts, including a cold `React.lazy` Suspense mount; the sixth failed once and never again, which is recorded in `REFACTOR_LOG.md` rather than smoothed away, because an unreproduced failure is the only thing that could re-open a withdrawn finding. **The give-away is an ordering claim that does not survive a timestamp**: the finding blamed `inert`, but on close `inert` is lifted 263 ms BEFORE the restore fires (the exit animation), with no inert ancestor at the call. Before fixing anything whose cause is "an effect ran at the wrong time", re-measure with StrictMode off — `npm run preview` is NOT the way to do it (it hits PROD Firebase, and is Patryk's job), so edit `main.jsx` locally and revert |
| A drag reproduced with browser automation | Cannot exercise anything that spans FRAMES. `TimelineBlock` coalesces pointer moves into one `requestAnimationFrame`, and the automation's press-move-release completes inside a single frame, so `endDrag` cancels that rAF before it runs and **the block is never lifted at all** — the visual half of a drag bug is structurally unreproducible that way, while the state-flag half reproduces perfectly. Two more traps in the same rig, both measured in v17.16.12: the pane's frame-to-CSS scale is NOT the emulated viewport ratio and it CHANGES when the pane is reopened, so calibrate it each session by clicking a known point and reading `e.clientX` from a capture-phase listener; and a single move jump lands on whatever is under the END point, so a cross-row drag never delivers a move to the SOURCE block and never arms. Same family as the synthetic `:active` press: what you measured was the tooling. **v18.0.0 phase 4 corrects "calibrate it each session" — that is not enough, and the correction is the whole of this addition.** A calibration went stale BETWEEN two consecutive tool calls with no reload, no `resize_window` and no navigation in between: a click computed from a K measured one call earlier landed 138,213 instead of the button at 270,416, and the "Turn off anyway" button silently did nothing. Measured afterwards, K is **not** drifting randomly — held at 1.0178 across three screenshot scales (1, 0.5, 0.4), a full page reload, and a modal opening — so the screenshot's `scale` argument does NOT set the click frame and page geometry does not move it either, which were the two obvious hypotheses and are both wrong. **What actually moves it was not reproduced and is therefore not claimed here**; the pane is a host UI panel whose physical size this session cannot read, and a stale K is silently wrong rather than loudly wrong, which is the worst shape. So the RULE is procedural, not explanatory: **never carry a K across tool calls.** Default to `javascript_tool` + `el.click()`, which needs no coordinates at all and drives a plain React `onClick` faithfully — verified this session, a module switch flipped and persisted to Firebase through it. Reach for coordinates ONLY when the interaction needs a real pointer (a drag, a press-and-hold, a `:active` state), and then arm a capture-phase `pointerdown` probe, click, and READ BACK where it landed before believing it; if it missed, correct by the measured ratio and verify again. A `.click()` is not a finger and never becomes one — that half of the rule is unchanged. One more mechanical detail: a page reload CLEARS the tool's cached screenshot dimensions, so the next coordinate click errors out until a fresh screenshot is taken |
| A control measured against a WRAPPED one | The number comes back exact and answers a question nobody asked. v18.0.0: the booking form's Date and Time were reported "misaligned by 11px" — which is `input[type=date]`.top − `input[type=time]`.top, measured correctly, and 11 is `DateField`'s OWN 10px padding plus its 1px border, because the date input is the transparent INNER control of a pill while the time input IS its pill. The two things a person actually sees were **0.00** apart at the top; the real defect was 1.84px at the BOTTOM and had a different cause (`mkInp` pinned no height). **Fixing the 11 would have changed nothing anybody can see.** `DateField` and `SearchField` both wrap an input this way, so a before/after on any form must compare the elements that PAINT the box — `closest('.mgt-datefield')`, never the `input` — or it measures the wrapper and reports it as the app. Same family as the automation-tree accessible name and the synthetic `:active` press: **check what your selector is holding before you believe what it returns** |
| A browser-automation `ref` captured before the page re-sorts | Is a row NUMBER, not a row. Measured v18.0.0 phase 6: saving one booking re-sorted the day, a `ref` taken before that resolved to a DIFFERENT card, and the resulting reading said a feature had failed when the booking it moved was simply not the one being read back. The give-away was the booking's own `history` entry naming the transition on a record nobody had opened. **Re-`find` after any action that can reorder a list**, and settle a "did this work" question against data the app itself wrote (a history entry, a stored field) rather than against the row you believe you clicked. Same family as the synthetic `:active` press and the accessible name read out of an automation tree: what was measured was the tooling |
